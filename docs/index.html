아키텍처

수집은 한 프로세스로 몰고 배포·적재·전략은 분리했습니다. 거래소 세션은 비싸고 끊기면 갭이 생기므로, 소비자가 각자 거래소에 붙으면 같은 데이터를 N번 받고 N배로 끊깁니다. 팬아웃은 로컬 IPC(Unix Domain Socket)로 합니다.

IPC
UDS
Unix Domain Socket pub/sub. 같은 호스트에서 TCP 루프백보다 빠르고, 파일시스템 권한으로 접근제어가 된다. 여러 호스트로 흩어지면 ZeroMQ 로 전환.
백프레셔
drop-oldest
구독자별 유한 큐. 차면 오래된 것부터 버리고 카운트한다. 느린 구독자 하나가 전체 배포를 멈추게 두지 않는다.
무결성
seq + CRC32
구독자별 연속 시퀀스로 갭을 탐지하고, CRC32 로 프레이밍 오류를 즉시 잡아 재동기화한다.
복구
snapshot+delta
접속 즉시 최신값 스냅샷을 보내고 증분을 잇는다. 갭을 만나면 재접속으로 재동기화.

운영에서 실제로 잡아낸 문제

증상진짜 원인조치
구독자 데이터 무결성 48% 게이트웨이가 심볼 필터링을 하는데 seq는 전역 번호를 그대로 사용 → 걸러진 번호가 구독자에겐 전부 유실로 보임 해결 구독자별 시퀀스 재넘버링 → 100.0000%
DB 지연시간이 −30,825µs 거래소 시계가 로컬보다 앞섬. 음수 지연이 든 테이블은 어떤 SQL 집계도 결론이 틀림 해결 최소값 필터로 시계 오프셋 추정·보정 (NTP 방식)
SIGTERM 후 프로세스가 안 내려감 Python 3.12+ Server.wait_closed() 가 핸들러 종료를 기다리는데, 핸들러는 큐에서 영원히 대기 해결 리스너 닫기 전 연결 핸들러부터 취소
종료 중 세그폴트 asyncio.to_thread 는 await 를 취소해도 스레드가 안 멈춤. 그 스레드가 쓰는 중에 DB 커넥션을 닫아 use-after-free 해결 DB 접근 경로 전체를 단일 락으로 직렬화
CRC 오류 후 세션 전체 정지 재동기화 직후 파서가 남은 버퍼를 더 안 읽고 반환 해결 재동기화 후 루프 계속 → 오염 프레임 1개만 폐기

전부 개발 중 참조 클라이언트와 통합 테스트가 잡아낸 실제 결함입니다. 상세 재현 절차와 조치는 저장소의 RUNBOOK.md, 설계 판단 근거는 DESIGN.md 에 있습니다.

직접 돌려보기

외부 패키지 설치가 필요 없습니다. python3 와 git 만 있으면 됩니다.

$ git clone https://github.com/oyeong011/market-feed-platform
$ cd market-feed-platform

$ make demo          # 6개 프로세스 기동 + 대시보드 안내
$ make status        # 서비스 상태
$ make client        # 참조 TCP 구독 클라이언트 (갭 탐지 포함)
$ make diag          # 장애 진단 원스톱
$ make test          # 109개 테스트 (네트워크 불필요)

# 인터넷 없이도 전 구간 재현 — 녹화 파일 리플레이
$ MDFEED_ADAPTERS=replay make demo

# 리눅스 서버 배포
$ sudo make install-systemd && systemctl start mdfeed.target
