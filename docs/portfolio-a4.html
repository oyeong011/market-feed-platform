상황 · 과제 · 행동 · 결과 · 배운 것
S
채용 요건의 대부분이 이 계층에서 나옵니다 — 프로세스 간 통신, TCP/HTTP, 리눅스 서비스 점검, 파이프라인 자동화. 요건에 "안다"고 쓰는 대신 동작하는 것으로 보이기로 했습니다.
T
기능을 늘리는 것이 아니라 네 가지 실패를 막는 것을 목표로 정의했습니다. 이 정의가 이후 모든 판단의 기준이 됐습니다.
  1. 세션은 반드시 끊긴다 — 끊긴 구간은 영구 유실. 거래소는 과거를 다시 주지 않는다
  2. 느린 소비자 하나가 전체를 멈춘다 — 한 구독자를 기다리면 전원이 굶는다
  3. 프로세스는 멀쩡한데 데이터만 안 온다 — 실제 장애의 대부분. systemctl status로 안 잡힌다
  4. 틀린 값을 조용히 배포한다 — 값이 없는 것보다 나쁘다. 아무 알람도 안 울린다
A
  1. 수집을 모으고 소비를 분리 — 소비자가 각자 거래소에 붙으면 같은 데이터를 N번 받고 N배로 끊깁니다. 거래소 하나의 장애가 전체를 내리지 않도록 venue 그룹별로 샤딩했습니다.
  2. 느린 소비자 격리 — 구독자마다 유한 큐를 두고 차면 오래된 것부터 버리되, 버린 건수를 반드시 셉니다.
  3. liveness와 readiness 분리 — Restart=on-failure는 프로세스가 죽어야 동작합니다. 헬스 판정 기반 워치독을 따로 뒀습니다.
  4. 품질 검사로 원칙을 집행 — 원칙만 있고 집행이 없으면 원칙이 아닙니다. 별도 프로세스가 6가지를 계속 검사합니다.
  5. 그리고 계속 측정했습니다 — 부하 시험, 장시간 감시, 장애 주입, 알람 검증.

I
  1. 문서를 믿기 전에 한 번 재본다 — KIS 문서는 체결구분 3이 매도라 했지만 실제는 5였습니다. 그대로 뒀으면 매도 체결이 전량 미상으로 남아 주문 흐름 지표가 통째로 무의미해졌을 것입니다.
  2. 근거 없이 적은 한계 서술은 없느니만 못하다 — "구독자 수백이면 재인코딩이 병목"이라 적어 뒀는데 재보니 CPU 0.28%였습니다. 그럴듯한 문장 위에 잘못된 최적화 계획이 쌓입니다.
  3. 계측 도구도 거짓말을 한다 — 알람 11개 중 4개가 영원히 안 울릴 상태였고, 장애 주입 테스트 하나는 아예 안 돌고 통과하고 있었습니다.

이 프로젝트에서 가장 값진 것은 기능 목록이 아닙니다. 문서가 틀린 곳, 측정이 거짓말하던 곳, 실제로 돌려봐야 드러난 곳입니다. 전부 참조 클라이언트·통합 테스트·CI·장애 주입에서 나왔습니다.

KIS 문서는 체결구분 3이 매도라고 명시합니다. 300건을 호가와 대조하니 5가 매도였고 3은 한 건도 나오지 않았습니다. 문서대로 뒀다면 매도 체결이 전량 미상으로 남아 주문 흐름 지표가 통째로 무의미해졌을 것입니다. → 관측된 기준으로 매핑, 미매핑 코드는 세어서 노출

거래소 시계가 로컬보다 앞섭니다. 음수 지연이 곧 데이터를 어떤 SQL 집계로도 되살릴 수 없다는 뜻입니다. NTP 방식의 최소값 필터로 venue별 오프셋을 추정해 보정했습니다. → 정상 범위 복귀
