02. 어떻게 접근했나
Approach.
채용 요건의 대부분이 이 계층에서 나옵니다 — 프로세스 간 통신, TCP/HTTP, 리눅스 서비스 점검, 파이프라인 자동화. 요건에 "안다"고 쓰는 대신 동작하는 것으로 보이기로 했습니다. 기능을 늘리는 것이 아니라 네 가지 실패를 막는 것을 목표로 정의했고, 이 정의가 이후 모든 판단의 기준이 됐습니다.

04. 실측으로 잡아낸 결함 — 26건 중 대표 5건
Debugging.
이 프로젝트에서 가장 값진 것은 기능 목록이 아닙니다. 문서가 틀린 곳, 측정이 거짓말하던 곳, 실제로 돌려봐야 드러난 곳입니다. 전부 참조 클라이언트 · 통합 테스트 · CI · 장애 주입에서 나왔습니다.
① 구독자가 받은 데이터의 절반이 무결성 실패 — 48.5%
게이트웨이가 심볼을 걸러 보내면서 시퀀스는 전역 번호를 그대로 흘렸습니다. 구독자 입장에선 갈 데 없는 갭이 계속 보입니다. 구독자별로 시퀀스를 다시 매기도록 고쳤습니다. → 100.0000%
② 국내 매도 체결이 전부 방향 미상
KIS 문서는 체결구분 3이 매도라고 명시합니다. 300건을 호가와 대조하니 5가 매도였고 3은 한 건도 없었습니다. 그대로 뒀다면 주문 흐름 지표가 통째로 무의미해졌을 것입니다. → 관측 기준으로 매핑, 미매핑 코드는 세어서 노출
③ 지연시간이 −30,825 µs — 음수로 측정됨
거래소 시계가 로컬보다 앞섭니다. 음수 지연은 어떤 SQL 집계로도 되살릴 수 없습니다. NTP 방식 최소값 필터로 venue별 오프셋을 추정해 보정했습니다. → 정상 범위 복귀
④ 벤치마크가 지연이 아니라 큐 적체를 측정하고 있었다
최대 속도로 밀어 넣고 지연을 재니 p50 105 ms. 지연이 아니라 기다린 시간이었습니다. 페이스 부하와 버스트 처리량으로 분리했습니다. → 지연 p50 47.3 µs
⑤ 알람 11개 중 4개가 영원히 안 울릴 상태였다
카운터를 0으로 초기화하지 않으면 첫 이벤트 전까지 시계열 자체가 없고, Prometheus는 없는 값을 0이 아니라 no data로 봅니다. 시작 시점에 카운터를 미리 선언하도록 고쳤습니다. → 알람 검증기를 CI에 편입
이 목록이 이 프로젝트의 알맹이입니다. 기능은 코드를 읽으면 압니다. 하지만 "문서가 틀렸다"를 어떻게 알았는가, "내가 쓴 한계 서술이 틀렸다"를 어떻게 발견했는가는 과정을 남겨야만 전달됩니다.

06. 판단과 범위
Decision.
직접 만든 것이 많다는 사실 자체는 자랑이 아닙니다. 어디를 직접 만들고 어디를 검증된 도구에 맡길지 판단한 근거가 이 프로젝트의 내용입니다.
직접 구현 vs 오픈소스
피드 프로토콜직접 구현
라이브러리를 써도 메시지 프레이밍 · 시퀀스 갭 탐지 · 스냅샷 복구 · 느린 구독자 격리는 어차피 직접 해야 합니다. 그 경계를 알려면 한 번은 아래까지 내려가 봐야 합니다.
분석 · 백테스트오픈소스
backtesting.py · vectorbt가 낫습니다. 우리가 제공하는 건 데이터와 전략 코드이고, 검증은 검증된 도구에 맡깁니다.
저장소오픈소스
PostgreSQL + TimescaleDB. 시계열 파티셔닝 · 보존정책을 직접 만들 이유가 없습니다.
관측오픈소스
Prometheus + Grafana. 우리가 만든 건 무엇을 지표로 내보낼지와 알람 규칙입니다.
정직하게 적는 범위
